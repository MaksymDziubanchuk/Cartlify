# Features

## Implemented Features

### Authentication and user flows

- user registration (the name is optional, up to 100 characters)
- the terms, the contract and the privacy policy of the shop: root publishes each new version (`POST /api/root/legal-documents`, `GET` lists them, the latest first); a version is never changed or removed, the database numbers it within its kind and keeps the sha256 of its text. A contract carries, besides its text, the days a buyer has to withdraw after the delivery (14 at least), the address the goods go back to and who pays the carrier for it (`contract`); a privacy policy carries how long each kind of personal data is kept, in days (`retention`); the terms carry neither, and a kind with the fields of another is refused. An order keeps the days and the payer of the contract in force at its confirmation. Anybody reads the versions in force (`GET /api/legal/documents/current`) and any version by its id. Nobody accepts the privacy policy: it informs, and no registration, login or order waits for it. The terms and the contract together have to give the right to withdraw within 14 days, how to withdraw and return the goods, who pays for the return and the model withdrawal form: their texts are the copy of the contract the buyer gets. While versions are in force, the registration takes the consent to all of them (`acceptedDocumentIds`: `400 LEGAL_ACCEPTANCE_REQUIRED` names the kinds missing, an old version is `409 LEGAL_VERSION_OUTDATED`; both name the versions in force with their titles). A login by Google, GitHub or LinkedIn that makes a new account takes the consent the same way: the page sends `acceptedDocumentIds` with the start of the login, the signed state carries them to the callback, and without them no account is made (the page gets `?error=LEGAL_ACCEPTANCE_REQUIRED`). A customer who comes back after a new version came in force accepts it at the login: a login with a password answers `409 LEGAL_ACCEPTANCE_REQUIRED` with the versions in force and the page logs in again with them in `acceptedDocumentIds`, a login by a provider gets the same code on its callback page and starts again with them; an admin or root is asked nothing. The confirmation of an order still checks it for a session that stayed open (`GET /api/legal/acceptances/me` names what is missing, `POST /api/legal/acceptances`). Each consent keeps the address and the browser of its request, the consents are only added
- email verification flow
- resend verification email: a new link each time, earlier links stop working; the links are stored only as hashes
- login / logout: logout ends the session of this browser, `allDevices` ends every session of the user
- refresh token rotation: `POST /api/auth/refresh` answers 204 and sets both tokens as cookies, no token in the body
- a session ended on purpose (a logout, a reset or a change of the password, a role change by root, a closed session) is a plain `401 REFRESH_TOKEN_REVOKED` when its cookie comes back, the other sessions go on; a token already renewed coming back was copied and ends every session (`403 REFRESH_TOKEN_REUSE_DETECTED`)
- sessions: `GET /api/auth/sessions` lists the open sessions of the user (the browser that opened each, its last renewal, its deadline, the current one), `DELETE /api/auth/sessions/:sessionId` ends one; a session keeps its id across its renewals
- data export: `GET /api/users/me/export` gives the signed-in person everything the shop keeps of them as one JSON file (profile, orders, favorites, reviews and votes, chats, logins, sessions, the consents to the terms and the contract; an item of an order names its product and its variant with the name and the prices the order was confirmed with, a favorite its variant and its product), once an hour unless `LIMIT_EXPORT_PER_USER` says otherwise; an item of an order is followed by the statements of withdrawal and of return made on it (the person's own words, data, money and the parcel they sent; never what became of the goods, what the shop paid to carry them back, the ids of the provider or the notes of the admins). Root gives the same file for another person, also for a deleted account, with `GET /api/users/:userId/export` (a line in the admin log). Database functions of the system, run by the periodic tasks, empty what is kept too long, each for the days the privacy policy in force gives (the shorter of the term when the data was collected and the term now, cleaned a day early; nothing without a policy): the address and the browser of old logins and of closed statements, the data of idle guests, the chats of accounts deleted long ago, the personal data of closed statements and the recipient of the orders of deleted accounts ([Returns](returns.md) says what stays)
- password change: `POST /api/auth/password/change` with the current password ends the other sessions, keeps this one, closes the reset links and mails the owner; a new reset link closes the ones mailed before, a reset closes them all
- a role change by root ends the sessions of the person; an access token of the old role the database refuses answers `401 ACCESS_TOKEN_EXPIRED`, the page renews the session
- forgot password / reset password
- OAuth entry points and callbacks for Google, GitHub, and LinkedIn; a callback sends the browser back to the frontend page `WEB_ORIGIN/auth/callback` (`WEB_PAGE_OAUTH_CALLBACK`), with `?error=<errorCode>` when the login failed
- guest-to-user data migration during login/OAuth flows
- guest chat continuity: the cart, the favorites and the chats of the guest move to the account at a login (password or OAuth) and at the verification of the email in the browser of the guest, not at the registration; registering an address that was registered before and never verified sets the new password and mails a new link
- the list of users for an admin or root (`GET /api/users`), root accounts included: every field of an account and its last login (`lastLoginAt`), an empty one is null; filters that go together — a part of the email in any case (`_` and `%` are plain characters), roles and providers (several through commas), the email confirmation, the deleted accounts (only with `deleted=true`); the order is the sign-up or the last login (`sortBy`, `sortOrder`), equal values go by id, accounts that never logged in come last; pages by cursor with the total of the filters
- the profile of a user by id (`GET /api/users/:userId`) depends on who reads it, in the database function and in the API alike: a user gets the name, the avatar and the dates, no email; an admin or root gets the whole profile but the password, the provider id and the avatar file id, the open chat of the user with an admin, and the lists the `include` checkboxes name (`orders`, `reviews`, `favorites`, `votes`, `loginLogs`, `consents` — the versions of the terms and of the contract the user accepted and the ones each order was confirmed with, with the address and the browser, the text of each by `GET /api/legal/documents/:documentId`) of a period: the last 30 days unless `from`/`to` come, any dates, at most 60 days long (`400 PROFILE_PERIOD_TOO_LONG`, `400 PROFILE_PERIOD_INVALID`)
- avatars: every answer that names an account gives `avatarUrls` in four sizes and `avatarIsDefault`: the own picture of the account, or, without one, the first letter of the name (of the email when there is no name) on a color of the account, the way a Google account shows it; a deleted account is G on grey. Cloudinary draws the letter at the url on a plain picture, nothing is stored per account; the server puts that picture into the Cloudinary folder of its environment when it starts, so a new Cloudinary account needs no step by hand
- the picture of a Google, GitHub or LinkedIn account becomes the avatar of a new account: on the login that creates the account the server downloads it from the provider (https on the hosts of the provider only, no redirects, 256 px, jpeg, png or webp by its content, up to 5 MB) and keeps it at Cloudinary as the avatar; it waits at most 4 seconds, and whatever goes wrong the login goes on with the drawn letter. A later login, or a login that links an account we have, takes no picture, so a removed avatar never comes back
- avatar removal: the owner removes the own avatar with an empty `avatar` in `PATCH /api/users/me` (JSON or a form field); a moderator removes the avatar of another account with `DELETE /api/users/:userId/avatar` — an admin from a user account, root from any account, through the database function `cartlify.remove_user_avatar`. The file goes from Cloudinary after the change. A removal by a moderator goes to the admin journal and mails the person which removal it is; the answer and the profile an admin reads give `avatarRemovals` and `avatarRemovalsLimit` (root sets it, `PUT /api/root/shop-settings`, 5 unless set), and past the limit the admin takes the account to root, who alone deletes accounts
- user profile read/update endpoints: the update takes JSON or a multipart form with an avatar file (jpeg, png or webp by its content, whatever type the form names, up to 5 MB (`UPLOAD_MAX_BYTES`), a bigger one gets `413 PAYLOAD_TOO_LARGE`; it replaces the avatar only once the profile is written, a refused request changes nothing), the name and the locale are up to 100 characters, the phone is empty (removes it) or exactly `+380501234567`-style, a plus and 8 to 15 digits, in JSON and in a form alike; ids in the path are whole numbers from 1 to 2147483647
- account deletion: a user deletes their own account (`DELETE /api/users/me`: the password of a local account, or a login of the last 10 minutes for Google, GitHub and LinkedIn; orders waiting for payment, paid or shipped are shown first and deleted only on a confirmed second request), root deletes any user except themselves. The row stays, emptied of everything personal, named Guest and marked with `deletedAt`: its owner can no longer change it, other users get `404 USER_NOT_FOUND` for its profile, an admin still reads it; an order waiting for payment is cancelled with its stock returned and its payment page closed, a payment that still comes is refunded in full; paid and shipped orders are delivered; favorites, reviews and chat messages stay, open chats are closed. The person gets a mail with the orders still on their way and what happened to the cancelled ones; an account already deleted answers `404 USER_NOT_FOUND`, a deletion by root keeps a line in the admin log, and the admin list of root names a deleted admin with its `deletedAt`
- login logging

### Authorization and security

- role model: `GUEST`, `USER`, `ADMIN`, `ROOT`
- Fastify route guards
- database-level row-level security policies
- per-transaction actor context passed into PostgreSQL
- cookie-based auth flow with HttpOnly cookies; the frontend and the API share one site (`shop.example.com` and `api.shop.example.com`), so the cookies are first-party and keep `SameSite=Lax`
- CORS and the chat WebSocket handshake let in only `WEB_ORIGIN`; images (the shop's logo, products, categories) come straight from Cloudinary, not through this origin check
- CSRF protection (double submit): `GET /api/auth/csrf` gives a token and keeps its secret in an httpOnly cookie, every `POST`, `PUT`, `PATCH` and `DELETE` sends the token in the `x-csrf-token` header or gets `403 CSRF_TOKEN_INVALID`; the Stripe webhook is exempt, it signs its own calls. Swagger UI adds the token by itself; in Postman or curl take a token first and keep the cookies between requests
- centralized error normalization and request/response logging

### Catalog and product management

The model in one page, for a developer and for a shop admin: [Products, variants and characteristics](variants.md).

- category listing and admin CRUD; the tree goes from the top down: a move takes the whole branch of a category, `parentId: null` moves it to the top, and a category never goes inside its own branch (`409 CATEGORY_PARENT_CYCLE`, refused by the database too, also for two moves at the same time); a new parent category gets its children one PATCH each; deleting a category gives its direct children to its parent
- an optional picture of a category (`PUT /api/categories/:categoryId/image`, a form with one file `image`, jpeg, png or webp by its content; `DELETE` takes it off; admin/root, both go to the admin log): the list, the tree and the answers of a category give `imageUrls` (three sizes, `null` without a picture), the old file is deleted when a picture is replaced or the category is deleted
- product listing with filtering, sorting and cursor pages, and the product details endpoint: a row of the list is `{ product, variant, minPrice?, maxPrice?, stock }`. It is a product row when the query asks nothing of a variant (a category, a search, the popularity, the rating, the news, the name, the sales, `inStock`): one row per product, with its main variant (the first by its place that has free units, the first of all when none has), the lowest and the highest price its variants sell at now and the free units of them all; it is a row of variants when the query asks something of a variant (a sort by the price, the discount or the end of a sale, a minimum or a maximum price, the filter by characteristics `f`, and for an admin the flags of the sale, of the free units of a variant and of the shipping data): the variants of one product that fit the query and have the same value of every MAIN characteristic are one row, a group (a variant without a value of a main characteristic is a value of its own, a product with no main characteristic is one group), with the first variant of the group by its place, the lowest and the highest price of the group (a price sort stands at the lowest going up and at the highest going down) and the free units of its variants; an admin sends `group=false` to see every variant on a row of its own. If variants must look different in a list, the characteristic that tells them apart must be main; what a buyer chooses by must be a choice from a list. The filter by characteristics (`f=12:45,46&f=15:128..512&f=20:yes`: values of a list, a range of a number with both ends included, yes/no; the values of one characteristic are OR, the characteristics AND; a variant without a value fits none; a text cannot be filtered; `400 FILTER_INVALID` names what is wrong) is also the filter of the change of the prices (`scope.f`). The panel of the filter of a category (`GET /api/products/filters?categoryId=`, `branch=false` for the category alone) is made from the variants a buyer sees there: a characteristic that is in the filters, is no text and has at least two different values, with the values that are there in the order of the admin, the lowest and the highest number, or yes/no, without counts. `total` counts the rows. A buyer (guest, user) gets the short variant, only the variants that are for sale and show a picture (a product with none is in no list), and what helps to buy (the price, the sale, the free units, the rating, the category; the list also the popularity) and sorts by date, price, popularity, rating, name or the sale (the variants on sale first, then the rest by the popularity of their product); admin and root get the full variant (the whole stock, the reserve, the units that are over, the cost of the latest delivery), the counters and the popularity override of the product too, sort by any field (the price by the usual one, the sale price in the list of the variants on sale) and list the deleted products, the variants on sale, the products with a popularity override that is on or the variants with no more free units than a number (`maxStock`) with their flags (an override goes with its end in the future, an end with an override) (without a flag only the plain products: not deleted, with no sale on any variant and no override that is on; with one every row of its condition). An admin also finds the gaps of the catalog with flags of the same kind: the variants that lack a value of a characteristic their category requires (`missingRequired`; the set of a category is its own and its parents', the nearest category winning for a characteristic), that lack the weight, any of the three sizes, the barcode or any picture (`withoutWeight`, `withoutDimensions`, `withoutBarcode`, `withoutImages`; the rows are variants), the products a buyer does not see (`hiddenFromBuyers=true`: removed, or none of its variants is alive with a picture) or sees (`false`), the products with a variant taken out of sale (`hasDeletedVariants`), and the products of a manufacturer, of a person responsible in the EU or that hold a document (`manufacturerId`, `euResponsibleId`, `documentId`; 404 when the party or the document is not there); a buyer who asks for one gets 403. A visit of an admin is not counted as a view
- two more sorts of the catalog, for every role: `sort=discount` (the variants on sale first, the biggest discount first with `order=desc`, then the rest by the popularity of their product; the rows are variants; an admin sorts the list of the sale flag by it) and `sort=sales` (the units sold in a period by the product, the best selling first with `order=desc`; the period is `salesFrom` taken in and `salesTo` left out, by default the 30 days up to the end of today (UTC); the orders paid in it that were not cancelled count; `SALES_PERIOD_INVALID` for a period that does not end after it starts; the cursor of a page carries no units sold, the server reads them for the row of the cursor again)
- admin product CRUD: a product holds what its variants share (the name, the description, the category, the manufacturer and the person responsible in the EU, the warnings, the documents, the popularity override) and each variant holds what is sold (the price, the sale, the stock, the article number, the barcode, the weight and the sizes, the pictures it shows); a new product and a product update never change the stock (`400 PRODUCT_STOCK_NOT_ALLOWED`): the stock comes with deliveries and goes with sales and write-offs
- variants of a product (a size, a colour, a memory): `POST /api/products` makes a product with its variants and its gallery from one form (`variants` is a JSON list of 1 to `PRODUCT_VARIANTS_MAX` variants, each names the files of its pictures by their numbers with a place of its own for each; every variant shows a picture, `VARIANT_IMAGE_REQUIRED`, every file is shown by some variant, `GALLERY_IMAGE_UNUSED`; a variant that is wrong is named with its own error in `400 VARIANTS_INVALID`, `details.variants`), `POST /api/products/:productId/variants` adds 1 to 100 variants at once, all of them or none, each at the next free place, `PATCH /api/products/:productId/variants/:variantId` changes the price (with the word on its sale), the article number, the barcode, the weight and the sizes, the place among the variants (the others move around it and keep a place of their own) and the pictures it shows (written whole; a variant left with none is hidden from buyers), `DELETE` takes a variant out of sale (it is only marked, it holds its place and lets its article number and its barcode go) and `POST .../restore` puts it back (`409 PRODUCT_SKU_TAKEN` or `VARIANT_BARCODE_TAKEN` when its code was taken meanwhile; a variant of a deleted product comes back only with its product, `409 PRODUCT_DELETED`). A barcode is 8, 12, 13 or 14 digits with a good check digit (`VARIANT_BARCODE_INVALID`), one live variant of the catalog has it at a time (`VARIANT_BARCODE_TAKEN`). A product has `PRODUCT_VARIANTS_MAX` variants at most (200 unless set, 10000 at most; the ones taken out of sale count), a variant shows `VARIANT_IMAGES_MAX` pictures at most (10 unless set, 100 at most). Requests over one product wait for each other (the row of the product, then its variants, then the pictures), so two deletes of one variant at once give one `200` and one `409`, and a picture taken out of the gallery while a variant is given it is a `400`, never a `500`. Every change of a variant is a line of the admin log of its own (`variant.create`, `variant.update` (`variant.update_batch` when it comes from a request of many) with the fields that changed, `variant.delete`, `variant.restore`)
- the card of a product (`GET /api/products/:productId`, `?variantId=` opens that variant) is `{ product, variant, variants }`: the part every variant shares, the variant opened in full and every variant to switch between in the short form. Without `variantId` it opens the main variant: the first by its place that has free units, the first of all when none has. A buyer sees the variants that are for sale and show at least one picture (a product with none, or a deleted one, is `404 PRODUCT_NOT_FOUND`, a variant he may not see `404 VARIANT_NOT_FOUND`); admin and root see every variant, the ones taken out of sale and the ones without a picture too, with `visible` and `deletedAt`, and the gallery of the product with the variants that show each picture. A visit of a buyer is a view of the product. `GET /api/products/:productId/variants/:variantId` gives one variant on its own
- what a variant weighs and measures packed (`weightGrams`, whole grams up to a ton; `lengthMm`, `widthMm`, `heightMm`, whole millimetres up to 10 m; the three sizes come together or not at all): a new variant needs them unless the admin says `withoutShippingData: true` (the flag is not kept), clearing what is known needs the flag too; the card and the variant on its own show them to everybody, `GET /api/products?withoutShippingData=true` (admin/root) lists the variants that lack them, and an alert counts them (`400 PRODUCT_SHIPPING_DATA_REQUIRED`, `PRODUCT_SIZES_INCOMPLETE`, `PRODUCT_WEIGHT_INVALID`, `PRODUCT_SIZES_INVALID`)
- search that forgives a typo and another order of the words and finds a product by the name of its category and by the article number of a variant too (admin and root by a barcode as well; letter case of an article number is ignored), the best match first (`sort: relevance`, the default with a search). A product row then shows the variant that has the code, and in a list of variants the search keeps the variants of the products found by their names and the variant that has the code; suggestions as one types (`GET /api/products/suggestions?q=`, up to 8 names of the products a buyer sees)
- category branches: a category in the filter takes the products of the categories below it (`branch=false` only its own), the card names the way to its category from the top (`category.path`), and `GET /api/categories/tree` gives the whole tree with the products of each branch (a product is counted when a buyer sees a variant of it)
- an article number (`sku`, optional, up to 64 signs) of a variant: one live variant of the catalog has it at a time whatever the case of its letters (`409 PRODUCT_SKU_TAKEN`); a delivery and a write-off may name a variant by it in place of its id
- a product taken out of the catalog comes back with `POST /api/products/:productId/restore` (admin/root, kept in the admin log, the answer is the card of an admin); taking a product out marks its variants that are for sale with the same time and the restore brings back just those (a variant an admin took out of sale before stays out; `409 PRODUCT_SKU_TAKEN` or `VARIANT_BARCODE_TAKEN` if a code was taken meanwhile and the product stays out); the admin finds the products taken out with `deleted=true`
- every sale names the lowest price of the 30 days before it (`salePriorPrice`, read from the log of prices of the variant), the price a reduction is compared with; `POST /api/products/sales` puts many variants on sale at once, each with its own sale, or all the variants of a product, or one sale for the variants of the products of a category and its branch, all or nothing
- documents of a product (instructions, certificates, declarations of conformity): PDF files kept as a directory (`/api/admin/documents`), checked by their bytes, stored on Cloudinary as PDF files up to `DOCUMENT_MAX_BYTES`; a product names them by their ids in an order of its own, the card gives them as `documents`, and a document a product names cannot be deleted
- the directory of characteristics a variant is described by (admin, `/api/admin/attribute-groups`, `/api/admin/attributes`, `/api/admin/attributes/:attributeId/options`): groups are the sections of the tab of a card; a characteristic has a type (text, number, yes/no, one value of a list, several of a list), a unit that is only a label, a number has digits after the point (0 to 3) and bounds, a characteristic may be shown in the filters of the catalog (`inFilters`) and a number, yes/no or one-value characteristic may be a main one (`isMain`) that splits the products of a list into rows; the values of a list have a name (one in the list, letter case ignored) and a colour for a swatch; groups, characteristics in a group and values keep an order the admin sets with one request; a name is one in its scope, letter case ignored; the type changes only while no values would be left without a list and no variant has a value of it; a group that has characteristics, and a characteristic a category asks for, cannot be deleted. A category asks for a set of characteristics (`GET` and `PUT /api/categories/:categoryId/attributes`, written whole, `required` per characteristic): a child category has the set of its parents and adds its own, the nearest category deciding one characteristic; the set is a hint to the form of the admin, not a ban. Every change is kept in the admin log
- the safety and origin data an offer shows in the EU (GPSR): the manufacturer and, for a manufacturer outside the EU, a person responsible in the EU are parties of a directory (name, postal address, email, country) that an admin keeps (`/api/admin/parties`); a new product names a party by its id or brings a new one, the card gives `manufacturer`, `euResponsible` and `warnings`; a change of a party shows in every product that names it, and a party a product names cannot be deleted
- stock in batches (admin/root), the stock of a variant: a delivery (`POST /api/products/stock/deliveries`) takes in a batch of each item at its cost of a unit in the money of the shop, with an optional last good day and the number the supplier gave it; an item names its variant by `variantId`, `sku` (its article number) or `barcode`, the cost and the last good day of the whole delivery stand in for an item that has none of its own, and the answer names the product and the variant of each batch; `source` is a supplier, a surplus an inventory found or goods a buyer brought back. A write-off (`POST /api/products/stock/write-offs`) takes free units of a variant from the batch named or from the batches in the order of a sale, with a reason (damaged, defective, expired, a shortage an inventory found, returned to the supplier, other with a note); the units the waiting orders hold stay. A sale takes the batch that ends first, then the ones without an end, the oldest first, and keeps what it took from which batch: the cost of the goods it sold; a cancel of a paid order puts the units back into the same batches. A batch whose last good day is behind the day of the shop (`SHOP_TIME_ZONE`) is over: its units are no free units anywhere a buyer looks or buys (the catalog, the cart, the confirm, the reserve, the bot), a payment of units held for an order whose batch got over meanwhile is refused and the money goes back, and an admin sees them apart (`expiredStock`) to write them off. All of a request or nothing; every step is a database function that keeps a line in the stock log for its variant (`stock.delivery`, `stock.write_off`, the sale at a payment `stock.sale` and the units back with a statement of return, also the cancel of a paid order, `stock.return` (and `stock.return_write_off` for those that went out again at once); see the journals below), and the server keeps one line for the whole delivery or write-off in the admin log (`STOCK_DELIVERY`, `STOCK_WRITE_OFF`: about the variant when the request touched one variant, about no thing when it touched more) with the same id as the answer (`deliveryId`, `writeOffId`), and the database checks that the stock of each variant is what its batches have left
- product images are the gallery of the product, and a variant shows the pictures of it that it picks: images come only as files of a form, jpeg, png or webp by their content, up to 5 MB per file (`UPLOAD_MAX_BYTES`) and `PRODUCT_IMAGES_MAX` in the gallery (50 unless set, 1000 at most); `POST /api/products` takes the files of the gallery with the product, `POST /api/products/:productId/images` adds more (they take the next places of the gallery and no variant shows them until it is told to, `PATCH .../variants/:variantId` with `images`), `DELETE /api/products/:productId/images/:imageId` takes one out (the variants that showed it lose it, the answer names the variants for sale left with no picture, `variantsWithoutImages`, and the file is deleted from Cloudinary). An upload waits at a temporary id and takes its place only once the rows are written (the transaction that writes them and moves the files is given 20 s and 2 s more for each file), a refused request leaves no files and the gallery as it was; a product that is not there and a gallery that is full are refused before the files are read, and the count and the places are taken under the lock of the product, so two uploads at once keep the limit; the files of the gallery are never overwritten, each lands at a path of its own
- the values of the characteristics of a variant (`attributes: [{ attributeId, value }]` when variants are made or changed): a text, a number within the digits after the point and the bounds of its characteristic, yes/no, a value of its list, or several values of a list; every refusal names the characteristic, the variant and the bound or the value (`ATTRIBUTE_VALUE_INVALID`, `_TOO_SMALL`, `_TOO_LARGE`, `_TOO_PRECISE`, `ATTRIBUTE_OPTION_NOT_FOUND`, `ATTRIBUTE_VALUES_REPEATED`, `ATTRIBUTE_VALUES_TOO_MANY` with `ATTRIBUTE_MULTI_VALUES_MAX`, `ATTRIBUTE_NOT_FOUND`), a request over several variants lists them all. The characteristics a category asks as required (with the parents') need a value when a variant is made and whenever its values change (`ATTRIBUTE_REQUIRED`; a requirement added later breaks no old variant, moving the product to another category checks nothing). Two live variants of a product with the same values of all the characteristics are refused (`409 VARIANT_DUPLICATE` names the variant that has them; one with no values repeats another with none), on make, add, change, restore and replace, under the lock of the product. The name of a variant and its `values` are written by the database from the characteristics that differ between the variants a buyer sees ("Phone X — 256 GB, black", main characteristics first); the card, the lists, the cart and the copy an order keeps at the confirmation read the same rule, a rename of a value or a characteristic changes them at once (a confirmed order keeps its copy), the card of a variant lists every characteristic it has in the order of the groups. A characteristic that a variant has a value of keeps its type and cannot be deleted (`ATTRIBUTE_TYPE_LOCKED`, `ATTRIBUTE_IN_USE` name the products), nor a value of its list (`ATTRIBUTE_OPTION_IN_USE`); a value is put in the place of another in all the variants at once, all or nothing (`POST /api/admin/attributes/:attributeId/options/:optionId/replace`, `VARIANT_DUPLICATE` lists the variants that would become alike)
- a variant without a picture is hidden from buyers, and a product none of whose variants a buyer may see (all taken out of sale or without a picture) is no part of what a buyer or a guest browses (the catalog, the suggestions, the favorites, the counts of the category tree, the products the bot names); its card is `404 PRODUCT_NOT_FOUND` for them. An admin opens the card and lists the product with `image: null`
- product category reassignment (`PATCH /api/products/:productId/category`, the answer is the card of an admin)
- sales (`PATCH /api/products/:productId/sale`, admin/root): the sale is the variant's. A discount by a percent of the price or an amount off it until an end in the future, for the variants named (`variantIds`) or every variant for sale of the product, each counted from its own price; `sale: null` takes the sales off. If the discount does not fit the price of a variant (an amount above it, a discount that comes to nothing) the whole request is refused and names those variants (`details.variants`). The answer gives the state of each variant (`set`, `unchanged`, `removed`); a request that leaves every variant as it was (the same sale again, or no sale to take off) is `409` and changes nothing. While the sale lasts the variant sells at the sale price (the cart, the confirmation and its smallest payment, the price sort and the price filters of the catalog), and the answers show `salePrice` and `saleEndsAt` next to the usual `price`; a sale past its end is left out. A new price of a variant on sale says what happens to the sale (`sale`: keep it, take it off, or a new one, each step with its log lines; the bulk price update keeps or removes the sales of every variant alike), without it the change is `409 PRODUCT_SALE_DECISION_REQUIRED`. The log of prices keeps the start of a sale (by its percent or amount, negative, with the end) and a sale taken off; the admin log keeps every sale as `PRODUCT_SALE` about the variant (started, changed, taken off, ended by a price down to it) with the price, the sale before and after and the discount. A free variant (a sale price of 0) is bought together with something that makes the smallest payment
- the price of a variant changes with the other fields of `PATCH /api/products/:productId/variants/:variantId` (a price with a sale that is on needs the word on the sale, a word on the sale needs a price; `price.set` in the log of prices and the line `variant.update` in the admin log), for several variants of a product the same way with `PATCH /api/products/:productId/variants` (`variantIds`, or every variant for sale) and for many variants of any products with `PATCH /api/products/variants/batch` (up to 100, each with fields of its own): all of them or none, and a refusal is `VARIANTS_INVALID` that names every variant refused with its own error (`details.variants`) under the status of the first one
- bulk price update endpoint for admin/root (`PATCH /api/products`, the usual prices): it changes the variants that fit the filter of `scope` (the category of the product, the products, the variants, the usual price, free units, taken out of sale or not), every one from its own price; `dryRun` lists the variants with their old and new price
- a change of many products at once (`PATCH /api/products/batch`, admin/root): up to 100 products, each with fields of its own, the ones of `PATCH /api/products/:productId` (the fields of the product, not the price, the sale, the article number or the weight, which are the variants') without images, with the same checks and log lines; all of them or none, a refusal names every product refused the same way in `details.products`
- an admin sees next to the price the cost of a unit in the latest delivery of a supplier (`lastUnitCost`, `null` without one; a surplus or goods a buyer brought back are no purchase) in the card, the list and the answers of the changes of a product
- product view/popularity-related fields in the data model

### Reviews and favorites

- product reviews, each with its author (`user: { id, name, avatarUrls, deleted }`); a deleted account stays the author, named Guest
- each review says whether its author bought the product (`verifiedPurchase`); the list sorts by the newest, the most helpful or the rating, and the mail of a delivered order asks to rate each product once, however many of its variants were bought
- review deletion rules for user/admin/root; a review an admin or root removes goes to the admin journal and mails the author which removal it is, of which product; the answer and the profile an admin reads give `reviewRemovals` and `reviewRemovalsLimit` (root sets it, `PUT /api/root/shop-settings`, 5 unless set), and past the limit the admin takes the account to root. An author deleting an own review is no removal
- the comment of a review is checked before anything is written, by two checks at once: a language model with the rules of the shop (obscene words in any language and form, insults, dangerous content, a text about another thing, ads, personal data; a negative opinion, rude words that are not obscene and questions about the product are published) and the free moderation of OpenAI (`omni-moderation-latest`) for the dangerous kinds alone, from a high score. A refused comment answers `400 REVIEW_COMMENT_REJECTED` with `details.reasons` and writes nothing, the rating of the request neither; a check that fails or is too slow lets the comment through and goes to the log without the text; without `OPENAI_API_KEY` or with `reviewCheckEnabled` false (root sets it) nobody is asked and the start warns about the key. 30 reviews a user an hour (`LIMIT_REVIEW_PER_USER`)
- a product removed from the catalog takes no new review (`404 PRODUCT_NOT_FOUND`)
- the reviews of a product a buyer does not see (removed from the catalog, or with no variant a buyer sees) answer a buyer `404 PRODUCT_NOT_FOUND`; an admin and root read them
- review voting endpoint: a vote is for the review of another user, the author gets `403 REVIEW_OWN_VOTE_FORBIDDEN`
- favorites for guest/user flows: a favorite is a variant of a product (`POST|DELETE /api/favorites/:variantId`, the same variant again answers 200 and is kept once; `404 VARIANT_NOT_FOUND` for a variant a buyer does not see: taken out of sale, without a picture, of a product taken out of the catalog). The list gives `{ product, variant, addedAt }` rows, the newest first, page by page: the product as the catalog shows it (with its popularity) and the short variant (its name, price, the sale while it lasts, the free units, the main picture). A person who likes two variants of one product has two rows and counts once in the popularity of the product. A variant a buyer does not see stays a favorite but is out of the list until it is back; the favorites of a guest move to the account at the login

### Orders

- current order/cart retrieval
- add/update/remove current order items: a position of the cart is a variant (`POST /api/orders/current/items` takes `variantId` and `quantity`; the black and the white of one product are two positions, the same variant again adds units to its position); a variant that is taken out of sale, whose product is removed, or that shows no picture is not found (`404 VARIANT_NOT_FOUND`); the free units are those of the variant (`409 OUT_OF_STOCK` with `details: { variantId, available, requested }`)
- a position of a cart or an order is `{ id, product, variant, quantity, unitPrice, totalPrice }`: the `variant` is the short variant of the catalog (its name, price, sale while it lasts, free units and its own main picture) with `forSale`; an order that is confirmed keeps the name and the price the confirmation fixed
- the cart shows current prices and loses the positions of variants a buyer does not see (taken out of sale, their product removed, no picture) for good, on every read and change; an order waiting for its payment, a paid and a delivered one keep them with `variant.forSale: false` (the payment page of the waiting order names the ones taken out of sale, `409 ORDER_ITEMS_UNAVAILABLE`)
- delivery: `GET /api/delivery/methods` lists what the shop offers (`deliveryMethods`, root sets it, `PUT /api/root/shop-settings`): `manual`, the shop sends the order itself by a carrier it works with outside the app, and `pickup`, the buyer collects it at the shop (`pickupAddress`, `pickupHours`); the manual method goes to the countries of `deliveryCountries` only
- confirm current order with its `delivery`: the method, the recipient (first name, last name, phone) and for the manual method the address in parts (country, postal code in the form of its country, city, street, house - its number, its name or both, or `s/n` for one without a number - apartment), a note is optional. Names are up to 100 characters with at least one letter and no digits, the phone is `+380501234567`-style like the profile phone. The cart offers the delivery of the last order of the buyer. An order that lost its reservation keeps its delivery for the next confirmation; a confirmed order keeps it as it was confirmed, the database refuses any change by the buyer (an admin corrects the person and the address of a paid order until it is sent)
- the delivery has a price (`deliveryFlatPrice`, free from `deliveryFreeFrom` of the items at current prices, a pickup costs nothing): the cart shows it for the items of now (`deliveryQuotes` for each method), the confirmation fixes it and adds it to the total (`itemsTotal` plus the delivery); the confirmation names the price the page showed (`expectedDeliveryPrice`, required), and a price that changed since is `409 DELIVERY_PRICE_CHANGED` with the price now; the minimum a payment provider takes counts the delivery, the payment page has a line for it and carries the recipient and the address
- the confirmation needs the consent to the versions of the terms and of the contract in force (`409 LEGAL_ACCEPTANCE_REQUIRED` with the kinds missing and the versions in force with their ids and titles: the page shows a checkbox for each and opens its text by id) and keeps the versions it was confirmed with, and the days to withdraw and the payer of the way back of the contract in force
- the confirmation names every item it cannot take (`409 ORDER_ITEMS_UNAVAILABLE` with `details.items: [{ itemId, variantId, reason, available, requested }]`: `deleted` when the variant is not for sale any more, `out_of_stock` when its free units are fewer than ordered; the stock, the price check `ORDER_PRICES_CHANGED` and the reservation are those of each variant)
- the confirmation refuses a total no payment provider takes (below 0.50 with Stripe) before any stock is held (`400 ORDER_TOTAL_BELOW_MINIMUM` with `details: { minimum, currency }`)
- the owner cancels the payment of an order waiting for it (`POST /api/orders/:orderId/cancel-payment`): the payment page is closed first by the provider that opened it, then the reservation goes and the order becomes `unconfirmed` with its items and delivery; a payment that came first answers `409 ORDER_ALREADY_PAID`
- an unconfirmed order (cancelled payment or expired reservation) is changed like the cart (`POST/PATCH/DELETE /api/orders/:orderId/items`), at current prices and without variants a buyer does not see, and confirmed again with only its id
- order history endpoint: newest first by default, the cart is not listed; paid orders keep the prices they were paid with, unconfirmed ones show current prices. `paidFrom`/`paidTo` keep the orders paid in a period (from its start, before its end, cancelled ones too; an end that is not after the start is `400 PAID_PERIOD_INVALID`), `sortBy=paidAt` lists the paid orders by the time of their payment; `updatedFrom`/`updatedTo` keep the orders changed last in a period (`400 UPDATED_PERIOD_INVALID` the same way)
- order by id endpoint
- every order answer (cart, confirmation, history, details, admin status update) gives the same fields: the `delivery` (method, price, recipient, address or the pickup place, note and, once the order is shipped, the send on its way: carrier, tracking number and link, never what the shop pays for it), while the order waits for the payment `reservationExpiresAt`, once it is paid `paidAt` (it stays) and once an admin cancelled it `cancelledAt`; the database sets both times, the payment id and the provider that took it stay internal. Admin and root also get every send of the order with its cost and whether the shop owes it (`shipments`) and what the order weighs (`weight`)
- admin/root order steps (`PATCH /api/orders/:orderId/status`, one at a time: paid, shipped, delivered, and one step back from each; no skipping): shipping an order by hand records the send (carrier, tracking number and link of the carrier, what the shop pays it; each optional, a number and a link each need the carrier, a link may come without a number), a pickup is shipped when it is ready to collect and delivered when collected; a step back takes the send back (`keepShippingCost` says whether the carrier is still owed for it; a mistake makes its cost 0, the cost it had stays in the admin log) and mails the buyer a fixed text; each step mails the buyer (the items, the total, the delivery) unless the account is deleted, a failed mail never undoes the status, a double click mails once
- an order answer gives the time of the delivery (`deliveredAt`: the step to delivered, or the earlier moment the admin gives with it, never of the future or before the send; taken away with the step back) and until when the buyer may withdraw by the contract (`withdrawalEndsAt`): the end of the last day, in the time zone of the shop, of the days of the contract the order kept (14 when none was published) after the day of the delivery; `withdrawalOpen` says whether the button of withdrawal works: a paid or shipped order always, a delivered one until that end and the days of grace (`withdrawalGraceDays`, root sets it, 4 unless set) after it
- `PATCH /api/orders/:orderId/shipments/:shipmentId` (admin/root) corrects the carrier, the number and the link of the send on its way (the buyer is mailed) and writes what the shop pays the carrier, also after the order was delivered or cancelled (never mailed); `PATCH /api/orders/:orderId/delivery` corrects the recipient, the address and the note of a paid order until it is sent (the buyer is mailed); every change goes to the admin log
- the cancel of an order by the shop is a statement of return (`POST /api/returns`, admin/root): with the reason `shop_cancel` (a paid order that was not sent) the goods go back to the stock at once, in the batches they were sold from, the order is cancelled when all of it is back, and the money goes back at once through the provider that took it (a refund the provider refuses leaves the order cancelled and the goods back, the card shows why and the admin tries again with `POST /api/returns/:returnId/refund`); with the reason `refused` (a shipped order, `basis` withdrawal) the statement takes whatever is left of the order and waits for the parcel and then for the money, and the order is cancelled when the parcel is back with all the money and the delivery. A delivered order is never cancelled, whatever came back. There is no route that cancels an order by itself
- the desk of the orders of an admin/root: the history filters by the buyer (`userId`), a few statuses (`statuses`), a product (`productId`: any variant of it) or a variant (`variantId`), the method and the country of the delivery, the carrier, the orders shipped without a number, with a delivery the buyer pays for, with a variant that has no weight, with a send whose cost is not written (and sent before a time, `shippedTo`) and a text (`q`: the number of an order, or a part of the email of the buyer, the name or the phone of the recipient, the city, the postal code or a tracking number); it sorts by the method, the destination or the price of the delivery too, and the orders with a send whose cost is not written by the oldest such send (the sort of that filter by default); each row names its buyer, `format=csv` gives every order of the filters as a file for the courier; `POST /api/orders/status` moves many orders by one step, each with its own answer. Each step goes to the admin log, and a double click mails once
- an order keeps the name each variant had when it was confirmed (`variant.name`, the copy the database keeps in `order_items."productName"`): the history, the mails, the CSV and the payment page show what was bought after a rename; an order not paid yet shows the price and the sale of each variant now, a paid one the price it was bought at; what an order weighs (admin and root) is the weights of its variants times the units, whole only when every variant has one; a cancel puts each unit back into the batch it came from, in the variant it was sold of
- the payment page has a line for each item and the email of the buyer; the payment carries the name of the shop (`shopName`, root sets it), as the mails do
- Redis-based timeout worker for order reservation expiry handling
- the buyer gets an email when the order is paid, with the delivery (the address and the recipient, or the place to collect it) (sent when the payment event of the provider comes; a failed mail never fails it); the texts of the terms and of the contract the order was confirmed with are attached to it as `terms.txt` and `contract.txt`, the copy of the contract, and its last line says so

### Shop settings

The data of the shop that root changes without a deploy lives in a database table, not the environment, a row a setting (the latest row of a setting is its value, nothing is ever changed or removed): see [shop settings](shop-settings.md) for the full model.

- `GET /api/shop-settings` (everybody): the fields the site needs — the name of the shop, the logo, the languages the shop answers in and the seller the pages must name; delivery (the methods, their prices, the pickup address and hours) is its own route, `GET /api/delivery/methods`
- `GET /api/admin/shop-settings` (admin, root): the current value of every setting but the internal id of the logo at Cloudinary; `GET /api/admin/shop-settings/missing` names the settings without a value and without a default that still wait for root, and the reply-to of the mails while it is blank (no mail goes out without it); the alert `shop_settings_incomplete` leads to it
- `PUT /api/root/shop-settings` (root): every setting at once, `PUT /api/root/shop-settings/:key`: one, `{ "value": ... }`; a row for each setting whose value changes, none for one given as it is (a value that breaks a rule, such as a free delivery from a sum with no price, a pickup without its address or hours not in their format, is `400` with a code naming the rule and writes nothing); `GET /api/root/shop-settings/history` pages through the rows of every setting or of one (`?key=`), each with who set it (the system, when the start filled a setting with no row yet)
- `POST /api/root/shop-settings/logo`, `DELETE /api/root/shop-settings/logo` (root): the logo as a file at Cloudinary (jpeg, png or webp by its content); without one the mails of the shop go without it, no request is refused for it
- a setting root has not filled in and that has no default of its own (the data of the seller, the countries of delivery) does not stop the start: a request that needs it is refused with its own code, and root and the admins see an alert until it is set
- the seller root filled in is named at the foot of every mail; the pickup hours, written in one format, are shown in the language of the mail

### Languages

The shop answers in more than one language: see [languages](languages.md) for how the server picks one and how to add another.

- the languages the shop answers in are a field of the shop settings above (`enabledLocales`), each with a dictionary file in the repository; root turns a language on or off without a deploy, the site's own language picker reads the same list from the public settings
- a signed-in person's own language (`locale` of the profile, settable at registration and with `PATCH /api/users/me`, filled in by a Google login) is used when it is one the shop answers in, else the shop's own language is used, else English; a guest always gets the shop's own language
- every mail of the shop (18 of them), the welcome and the fixed replies of the chat bot, and the language Stripe opens its payment page in, all follow this same rule
- the chat bot itself answers a written question in whatever language the customer wrote it in, regardless of their own saved language

### Payments

Payments go through payment providers, none of them is the main one: the buyer names the provider to pay with. The server has Stripe for now; each provider keeps its own routes under `/api/payments/<provider>/`, the order records which provider took its money (`paymentProvider` with `paymentId`) and refunds go back through it.

- `POST /api/payments/checkout/sessions` with `orderId` and `provider` (required, `stripe` for now) opens the payment page of an order waiting for its payment; a repeated request for the same confirmation and provider gives the same page, a page of another provider opened before is closed first; so is a page whose values changed since it was opened (the buyer changed their language, root changed a setting the page carries): it is closed and a new one opened, never two payable at once. The answer names the `provider` of the page
- a total below the minimum of the provider is refused with `400 ORDER_TOTAL_BELOW_MINIMUM` (0.50 with Stripe; the confirmation refuses a total no provider takes already), an item whose variant was taken out of sale with `409 ORDER_ITEMS_UNAVAILABLE` as in the confirmation (a line of the page is a variant, named by the name of the confirmation); the provider out of reach answers `503 PAYMENT_PROVIDER_UNAVAILABLE` and opens nothing

Stripe:

- a Stripe page returns the buyer to `WEB_ORIGIN/checkout/success?session_id=<id>` or `WEB_ORIGIN/checkout/cancel?orderId=<id>`; the pages of the frontend the server links to and sends the browser back to are settings (`WEB_PAGE_*`, the paths above unless set), a path of the site from `/` (a value that leaves the site stops the start); a confirmed order holds its units 15 minutes (`reservationMinutes`, root sets it), stripe keeps its page open 30 minutes after that (`stripePageMinutes`)
- `GET /api/payments/stripe/checkout/sessions/:sessionId` tells the page the buyer comes back to how the payment stands; Stripe is asked directly, it knows about the payment before the webhook comes. An id that is not one of a Stripe checkout session is refused with `400 VALIDATION_ERROR` before Stripe, a session Stripe does not have or one not opened for an order answers `404 CHECKOUT_SESSION_NOT_FOUND`
- `POST /api/payments/stripe/webhook` (Stripe signature, no CSRF token, outside the request rate limit; the webhook endpoint of the Stripe account points here) records the payment, returns a payment the order cannot take in full and releases the reservation of a closed page after the grace window; the same payment delivered again changes nothing, also after the order was shipped, delivered or cancelled; a page of another tool in the same Stripe account is acknowledged with `skipped: NOT_AN_ORDER` and its money is left alone

### Chat and AI assistant

- current chat thread endpoint for guest/user sessions: two tabs that open it at once get the same chat; it gives the newest 50 messages, the ones before come page by page from `GET /api/chat/threads/:threadId/messages` with `nextCursor` (a customer reads their own chats, an admin the chats given to the admins)
- WebSocket connection endpoint for realtime messaging: the message of the customer reaches the chat as soon as it is written, the answer of the bot after it; one turn of the bot at a time in a chat, a message sent while the bot answers is refused with `CHAT_BOT_REPLYING` and not kept
- thread join/read/message events
- bot welcome message for newly created chat threads
- guest and authenticated-user chat flows
- OpenAI-powered chatbot responses
- product-aware bot answers based on product context: the bot knows only what a buyer sees (a product of the catalog, its variants that are for sale and show a picture) and a product with a unit free to buy; of each variant it knows the name, the price, the sale while it lasts and the free units, and it recommends a concrete variant. It names up to 20 variants of a product one by one (those with free units first) and sums up the rest; a long description is cut. The items of the orders it knows carry the names they were confirmed with
- automatic response language matching based on the latest customer message
- bot fallback behavior when AI response generation fails (an answer the model cut short is not asked again)
- the bot knows the last 5 orders of a signed-in customer, read with the rights of that customer
- the answers of the bot a guest and a user get in 24 hours are limited (`CHAT_BOT_GUEST_DAILY_TURNS`, `CHAT_BOT_USER_DAILY_TURNS`); past them the bot answers with a text of its own and the model is asked nothing. A user who has not confirmed the email has the limit of a guest
- a new cookie or a new account does not start the day again: the turns of guests and of users with an unconfirmed email are counted by the address too (`CHAT_BOT_IP_DAILY_TURNS`, 60 a day from one address, an IPv6 address by its /64 network), and the whole shop has a ceiling of turns that call the model in a day (`CHAT_BOT_SHOP_DAILY_TURNS`, 3000): past it the bot answers with its fallback text and the model is asked nothing. A request for a person is answered with the text of the app as before. The counts live in the memory of the server (a restart forgets them). The answer of the model is bounded too (`OPENAI_MAX_OUTPUT_TOKENS`, 450 unless set; the fixed texts of the bot 120)
- admin escalation flow: before the model only an explicit request for a person and a question said a third time (more than three words) are found; whether anything else needs a person the model decides by meaning. A customer with a confirmed email is asked to describe the issue, the chat goes to the admins with the same step as that answer, and the description is what enters the admin queue (`admin:requested`)
- guest admin-support guard: only customers with a confirmed email talk to an admin, a guest or a customer without one is told so
- admin queue state model based on `adminRequestedAt` (asked for an admin, not taken yet) and `adminUnreadSince` (the oldest message no admin has read; an admin who opens, reads or answers a chat clears both)
- message read-state handling for bot/user/admin chat scenarios

### Admin and root capabilities

- the journals (admin/root, the same lines with the same filters for both; an admin does not see who root is in them: its id is 0 and its name, email, address, browser and the values of the changes of its account are the word `hidden`, the role stays, the answers have the same shape): the admin log (`GET /api/admin/audit-log`), the stock log (`GET /api/admin/stock-log`: a line for every change of the quantity of a variant, with the change, the stock after it, the event, the id of the delivery, of the write-off or the order it belongs to, who did it (nobody for the sale at a payment) and what it was made of, only added to; filters `productId`, `variantId`, `deliveryId`, `writeOffId`, `orderId`; the batches, the movements of the stock and the accounting report read it), the log of prices of every variant (`/price-log`, a line for each variant with its product and variant, filters `productId` and `variantId`), of logins (`/login-log`) and of consents (`/consent-log`; a customer reads their own logins and consents in their sessions and export). Each line has an `event` that says what made it, finer than the action (`product.update_batch`, `order.ship_bulk`, `login.google`, `consent.order`; `GET /api/admin/log-events` lists them for the checkboxes). Every journal sorts by any simple column both ways (`sortBy`, `sortOrder`), reads a period, takes the events asked for (`events`) and the columns asked for (`columns`), pages by a cursor that holds its sort and gives a csv of the filters; the history of the price of one product is `GET /api/products/:productId/price-history` (each line names its variant, `?variantId=` keeps one variant)
- alerts in place of mails (`GET /api/admin/alerts`), the overview of the work of an admin: paid orders to ship, orders sent by hand and not delivered for some days, pickups not collected, sends whose cost the shop has not written, variants with no or few free units (a variant taken out of sale is none), variants that lack the weight or the sizes, variants that lack a characteristic their category requires, products of the catalog none of whose variants a buyer sees (a product removed on purpose is not one), batches near or past their last good day (those of a variant taken out of sale too), chats with a message no admin has read, late payments given back in some last days, a reservation worker that stopped; root also the actions of the admins. Each kind comes with its count and the request to the list of the app with its cases (`list`: the orders, the catalog of an admin, the batches, the chat queue, the admin log), the most urgent first; the page of an admin shows a few rows of each, sorts them as that list sorts and leads to the list or to a case. `?subscribed=true` gives only the kinds the admin follows, for the notifications the frontend shows at the interval the admin chose when a count changed
- the statements of withdrawal and of return for the admins (`GET /api/returns`, admin/root): a page at a time with the total of the filter and a csv file, each line with the buyer, the units and the money by what became of the goods and of the money, the days since the statement; filters by state, goods (waiting, no proof, proof not confirmed, received), money (not back, pending, failed, back, refused), source, basis, reason, order, buyer, product, variant, a text, the periods and the days the alerts use; the alerts of the statements (`failed_refunds`, `returns_manual_check`, `returns_proof_waiting`, `returns_goods_not_sent`, `returns_money_late`, `returns_goods_late`) and of the orders shipped by hand with no tracking number (`shipped_without_tracking`) name the list with the filters of their cases, so the count of an alert is the total of its list; the list of orders filters and sorts by the status of the statements of return (`returnStatuses`, `sortBy=returnStatus`); the profile of a user for an admin counts their statements and names the list
- the settings of the alerts, each admin and each root their own (`/api/admin/alerts/subscriptions`): follow a kind or not, set its threshold within its bounds (days, units, seconds, hours) or give it back to the one the server gives (`PUT`/`DELETE .../:kind/threshold`); single cases put aside (`/api/admin/alerts/dismissals`, kept in Redis) leave the count of their kind until taken back or over
- admin stats endpoint (`GET /api/admin/stats`, admin/root): the users (the accounts of buyers, admins and root left out), the orders by status, the money paid in a period and in the last 7 and 30 days (the delivery paid for is part of it and also given apart; a cancelled order stays in the period it was paid in), what went back with the returns in the same periods (by the time the money went back), the units sold and the average order of the period, the top products (a product is the sum of all its variants), the top variants (each as `{ product, variant, revenue, quantitySold }`) and the top categories of the net money (the sales less the returns) of the period, the reviews and their average rating of the period, and `money`: the income, the expenses and the margins of the period, the same as `summary` of the accounting report for it; the period is `[from, to)`, all time until now unless given
- accounting report (`GET /api/admin/reports/accounting`, admin/root): for a period (`from` taken in, `to` left out; all time until now without them) and the products (`productIds`: all their variants) or the variants (`variantIds`) asked for or all: the sales of the orders paid in it (cancelled later or not) with their cost at the batches they took and the margin, the returns (the rows of the statements whose money went back in it, by the time it went back: their money and the cost of the units that came back, by the kind of the statement), the net (the sales less the returns), `summary` with the income (the net items, the delivery less what went back), the expenses (the cost of the goods kept, the write-offs, the sends) and the margins (the items, the delivery, the total), the batches taken in by source, the units written off by reason at their costs (also the goods that came back and went out at once), and the stock read from the stock log (at the start of the period, what came in and went out, at the end, and the units on their way back); every event is in the period it happened in, so a past period never changes; `categoryId` keeps a category, with its whole branch unless `branch=false`; a report of the whole shop also has the delivery (`delivery`): what the orders paid in the period paid for it, told apart what went back with the returns (by the time the money went back), what the sends cost the shop (by the time they were sent; the ones without a cost written are counted apart) and what is left, none for a report of some products or of a category
- the batches of the stock and its journal (`GET /api/admin/stock/batches`, `/movements`, admin/root): each batch of a variant (every row names its `variant` with its `product`) with what it came in with, what is left of it at its cost, what the paid orders took and what was written off, its delivery (supplier, invoice, note, the admin) and whether it is over, filtered by product (all its variants), variant, delivery, source, units left, over or ending by a day and sorted by when it came in, its last good day, what is left, its cost or its value; the journal puts the deliveries, the write-offs, the units the paid orders took and the units their cancels put back in one list by time, filtered by product, variant, batch, order, delivery, write-off, kind and period, with the batches and the change of the stock and of its value
- accounting by product, variant, category and time (`GET /api/admin/reports/accounting/products`, `/variants`, `/categories`, `/timeline`, admin/root): the same money for each row, the margin of the sales, the returns and the net, the write-offs and the margin after them, the stock of the period; a row of the report by product is a product, the money of all its variants added up (`{ product, category }`), a row of the report by variant is a variant with its product (`{ product, variant, category }`; its rows add up to the rows of the report by product and its totals are theirs), a category and a step of time add up the variants; `productIds` and `variantIds` keep the variants of those products or those variants; rows sorted by revenue, margin, its percent, units, margin after the write-offs, write-offs, purchases, stock or name with cursor pages and totals; categories with their whole branch or their own products only; the days, weeks from monday or months of the calendar of the shop (`SHOP_TIME_ZONE`, Europe/Madrid unless set), up to 400 steps. the steps of time carry the delivery and their `summary` too. `format=csv` gives each as a file for the accountant

### API documentation

- Swagger UI for REST API documentation
- OpenAPI 3.0.3 specification generation
- grouped route documentation by domain module
- reusable response schemas for system endpoints
- cookie-based security schemes for access token, refresh token, and guest id flows, plus the `x-csrf-token` header on every route that changes data

- documented system readiness responses for healthy and unavailable states
- raw OpenAPI JSON endpoint for external inspection and tooling
- Swagger documentation is deployed together with the running API
- every operation has a summary, a tag, a unique operation id and a description, and every parameter and every answer is described; the error codes of a route are named next to its statuses as "`CODE`: why", and the refusals all routes share are added by the OpenAPI plugin
- the document is held to the code by tests: every answer of the app in the integration tests is checked against it, and `openapiComplete.test.ts` checks the whole document (the descriptions, the codes it names, the examples against their schemas, the kinds of alerts)
