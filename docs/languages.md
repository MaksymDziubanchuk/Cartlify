# Languages

This page explains how the server picks a language to answer in, and how a mail, the chat bot and the Stripe payment page use it, to a developer who builds the frontend, to a translator, and to the shop owner. The field that turns a language on or off is part of [shop settings](shop-settings.md); the routes and the error codes are also in [API](api.md) and in Swagger (`/documentation`).

## The shop answers in more than one language

Cartlify ships with three languages: English, Spanish and Ukrainian. Each has one dictionary file, `en.json`, `es.json` and `uk.json`, in `src/locales/`; English is the base language and is always there (the server does not start without it). Root turns a language on or off for the shop from `enabledLocales` ([shop settings](shop-settings.md)) without a deploy — a language can sit in the repository switched off until its translation is checked, and switching one off never changes the saved language of a person who already picked it, it only stops new mail going out in it (see below).

**Adding a language** is a translation, not a code change: drop a new dictionary file next to the others, named by its two-letter code (`fr.json` for French), with every key the base language has (see "The dictionaries" below; a test catches a forgotten key before it ever reaches a mail), deploy, and have root turn the language on in the admin pages. No table, no route and no line of the server itself names a language by its code; the whole list root may choose from is simply the files in the folder (`AVAILABLE_LOCALES`, `src/config/locales.ts`, read once at startup).

## Whose language it is

A **guest** has no language of their own; their mail, the chat bot and their payment page always answer in the shop's own language, `shopLocale`.

A **signed-in person** may have one, saved as `locale` on their profile (two lower-case letters; `uk-UA`, `UK` and the like are read down to `uk`, anything else is dropped). It comes from three places:

- **registration** (`POST /api/auth/register`) takes an optional `locale`; one the shop answers in is saved and the confirmation mail already goes out in it, one the shop does not answer in (or not shaped like a language at all) is simply not saved — registration is never refused for it, because the confirmation mail has to go out before a browser would have had the chance to set it with a second request;
- **a login with Google** fills it in from the account's own language the same way, while the profile has none (a language saved before, by the person or by an earlier login, is never overwritten); GitHub and LinkedIn tell the server nothing of a person's language, so it stays empty;
- **`PATCH /api/users/me`** lets a person set or clear it at any time (`400 LOCALE_INVALID` for one the shape is wrong or the shop does not answer in, `400 LOCALE_TOO_LONG` for a value over 100 characters before it is even parsed).

A language that is **not** one of `enabledLocales` is never saved: registration and a Google login do not refuse it, they simply do not keep it, while `PATCH /api/users/me` refuses it (`400 LOCALE_INVALID`), because there the person picked it on purpose and should be told; so is one with no dictionary file at all, though that should not happen once root can only turn on a language that has one (`shopSettings().enabledLocales`, the shape checked by the database, the dictionary checked by the server, `src/helpers/locale.ts`'s `enabledLocaleOf`). If root later turns a language off, nobody's saved `locale` changes; mail to that person simply stops going out in it from that point on, as if they had never set one.

**The language a mail, the bot or a payment page actually use** (`mailLocaleOf`, `src/helpers/locale.ts`) is: the person's own saved language, if the shop still answers in it; otherwise the shop's own language, `shopLocale`; otherwise English, if even the shop's own language somehow lost its dictionary file after a deploy (the alert `shop_locale_missing` tells root and the admins when that happens). A guest always starts at the second step, having no language of their own.

## The dictionaries

A dictionary file is flat JSON, grouped into namespaces (`verifyEmail`, `orderPaid`, `chatBot`, and so on, one broadly per mail or feature), each holding `key: phrase` pairs — **text only, never HTML**: the layout of a mail stays in its own `.html`/`.txt` file (`src/services/email/templates/`), a dictionary only supplies the words that go into it. A phrase may hold `{{marks}}` of its own (`"Order #{{orderId}} is paid"`), filled in by the code that asks for it ([i18next](https://www.i18next.com/)); a handful of phrases that need a count (how many days are left to withdraw) use the suffixes i18next itself understands, `_one`, `_few`, `_many`, `_other`, one phrase per form a language's own grammar needs — English and Spanish need two of the four, Ukrainian needs all four. Frequently repeated phrases (a greeting, a button, a table header, "Questions? Write to us…") live once under `common`, read from every mail that needs them, rather than once per mail: fewer phrases to translate, one phrase to fix if it is ever wrong.

**Reading a phrase** (`t(key, locale, values?)`, `src/config/i18n.ts`) looks the key up in the dictionary of `locale`, falling back to English for a key the chosen language's file does not have at all (so a language can lag a day behind a brand-new phrase without breaking); a key that is in **no** dictionary at all throws (`EMAIL_DICTIONARY_KEY_MISSING`) rather than showing the bare key to a customer — a mistake in the code or in the template, never something a mail should ever carry.

**Adding a mail, or a phrase to an existing one,** means adding the key to **every** dictionary file at once, in the same change: `tests/unit/config/i18nDictionaries.test.ts` checks that every key the English file has is in every other file too, with no language left with an empty phrase, and that the `{{marks}}` of a phrase are the same ones in every language (a translation that drops or adds a substitution is a bug, caught here rather than in a mail someone actually receives). A language may hold extra keys of its own only for the plural forms its own grammar needs beyond English's (Ukrainian's `_few`/`_many` on top of `_one`/`_other`) — anything else left over in one language and not in English fails the same test.

**Dates and money** in a mail or on a payment page are not part of the dictionary: they are formatted with `Intl.DateTimeFormat`/`Intl.NumberFormat` given the recipient's own locale, so "17 October 2026" becomes "17 de octubre de 2026" in Spanish and "17 жовтня 2026 р." in Ukrainian without a translator ever touching a date. English keeps its existing `en-GB` date style (day before month) rather than switching to the `Intl` default for a bare `en` locale, so English mail reads exactly as it always has. The few words the server itself puts into a phrase are dictionary phrases too, never English slotted into another language: how long a mailed link lasts (`common.minutesCount`/`hoursCount`/`daysCount`, each count in the form its language takes: "24 hours", "24 годин", "24 horas"), the apartment in an address (`common.apartment`), and the first line of a mail, by name or without one (`common.greeting`/`greetingNamed`, so each language sets the name off its own way).

## Mail

All 18 mails of the shop (one folder of `src/services/email/templates/` per topic) build their subject, their `.html` and their `.txt` from the dictionary, in the recipient's own language by the rule above. The one exception that needs its own care: the mail that tells a person their account was deleted is sent **after** the deletion has already wiped `users.locale` from the row, so the language is read and kept aside before that happens, not from the row as it stands when the mail actually goes out.

## The chat bot

The bot's welcome message, when it opens a brand new chat, follows the same rule as a mail: the signed-in customer's own language if the shop still answers in it, the shop's language for a guest or for anyone else. So do its **fixed replies that never call the AI model at all** — the daily limit used up, a request for a human admin answered without asking the model, a possible repeated question — because there is no model call in those cases from which to read what language the customer is even writing in.

The model itself, when it is asked, is given its own instruction to answer "in the same natural language as the latest customer message", explicitly **not** the customer's saved `locale`: a person may have an account set to Spanish and still be typing in English right now, and the bot should answer the language actually in front of it, not the one on file. The same instruction covers the handful of fixed-**meaning** replies the bot still asks the model to phrase naturally (the exact wording of "please describe your issue for an admin", for instance) — the model phrases the meaning in the customer's own written language, and only when that very call fails does the reply fall back to the dictionary phrase in the customer's saved language instead.

## The Stripe payment page

`POST /api/payments/checkout/sessions` opens the page in the buyer's own language the same way a mail would (`mailLocaleOf`), **when Stripe Checkout itself has that language** — Stripe's own list of supported languages does not match the shop's one-for-one; at the time of writing it has no Ukrainian, so a Ukrainian-speaking buyer's page opens in `auto` instead (Stripe's own guess from the browser) rather than in English. The check is against the real list the installed Stripe SDK's own types carry, not a hand-kept copy of it, so a future SDK update that drops a language is caught by the typechecker rather than silently sending Stripe a code it no longer recognizes.

## Checks, in the database and on the server

The **shape** of a language code — two lower-case letters, nothing else — is a database `CHECK`, on `users.locale` and on `shopLocale`/`enabledLocales` of `shop_settings` alike; a `CHECK` cannot reach out to the filesystem, so it cannot know whether a dictionary file actually exists for a shape it accepts. **Whether a language is one the shop actually answers in** — enabled, and with a dictionary file that still exists — is checked by the server instead, at every point a language is saved or chosen (`enabledLocaleOf`, `src/helpers/locale.ts`): registration, `PATCH /api/users/me`, a Google login, and root's own `PUT /api/root/shop-settings` (which additionally refuses turning on a language with no dictionary file at all, `400 LOCALE_NOT_SUPPORTED`, because that one genuinely is a mistake worth refusing, not silently dropping).
